# 数据存储、备份与升级（v0.6.2）

> 这份是 v0.6.0 那版的**增补与更正**，重点写四件事：
> ①写入规则（0.6.1 定下） ②0.6.2 把事实卡的修改轨迹写进库（schema v3） ③备份到底备了什么、没备什么 ④容量边界（**不承诺无限容量**）。
> 基础结构（三张表、分页游标、`delete` 回滚日志）见《数据存储与备份-v0.6.0.md》，仍然有效；表结构版本以本文第 5 节为准。

## 1. 存在哪里

| 内容 | 位置 | 备份是否包含 |
| --- | --- | --- |
| 聊天记录 / 重点信息 | `%APPDATA%\ai-conversation-copilot\history.db` | ✅ 包含 |
| 设置（含 API Key，DPAPI 加密） | 同目录 `settings.json` | ❌ **不包含** |
| 个人读音词表（`customReadings`） | 同目录 `settings.json` 里 | ❌ **不包含** |
| 日志 | 同目录 `logs\app.log` | ❌ 不包含（也不该备份进交付物） |
| 音频 | **不存** | — |

**这是最容易搞错的一点**：界面「记录 → 备份」用的是 `VACUUM INTO`，它只导数据库。
**你存下来的「我的读法」不在备份文件里。** 换机器或重装想带走词表，
要另外把 `settings.json` 复制走 —— 注意它里面有加密后的 Key，别随手发出去。

## 2. 写入规则（v0.6.1 定下、v0.6.2 补上事实卡）

| 改动 | 之前的问题 | 现在的行为 |
| --- | --- | --- |
| AI 回复只在**写入回执成功后**才从待写队列里移除 | 数据库还没确认成功就把「待写回复」清掉了；失败后重试的那一批里不再包含这条回复，**回复永久丢失** | 失败保留完整待写批次（含回复），自动重试与手动重试都会把它补上 |
| 「未提供」与「明确清空」分开 | 后到的更新分不清「这个字段没给」和「用户把它删空了」，一律按「没给」处理，导致**清空操作被旧值复活** | 新增 `cleared` 白名单：没声明清空的字段一律不覆盖；声明清空的字段在 upsert 后补一条 `UPDATE` 真正置空 |
| 音源通道记录真实来源 | 一路都写 `system`，现场沟通（麦克风收对方的话）也被记成系统声音 | 现场模式记 `mic`，系统回环记 `system` |
| 空值不覆盖非空 | 译文晚到时会把已存的回复冲成空 | `excluded.x` 为空时保留旧值 |

这三条都有回归用例：`history` 组 126 条（含 K21–K24：不声明清空不覆盖 / 声明清空真清 / 重开库后仍然成立）。

v0.6.2 新增一条：**事实卡的修改轨迹要真的落盘**。

| 改动 | 之前的问题 | 现在的行为 |
| --- | --- | --- |
| 事实卡存「原话 / 改前值 / 被否定关系 / 状态 / 确认时间 / 动作日志 / 现在该怎么说」 | 库里只有 value / source_text / certainty / confirmed / edited；`confirmedAt` 与修改记录只在内存里，重开就没了 | schema v3 增加 11 列；日志以 JSON 存 |
| 删除事实要真删 | 只做 upsert，用户删掉的事实重开又回来 | 保存时带 `removedIds`，按 id 删除 |
| 事实卡单独报保存状态 | 字幕存成功就显示「已保存」，掩盖了事实卡写失败 | 卡片底部独立显示「事实卡：已保存 / 尚未保存（重试）」 |

## 3. 容量边界（不承诺无限）

说清楚三件事：

1. **软硬上限**：数据库文件大小受磁盘剩余空间限制；单进程内存受这台机器的可用内存限制。
   我们**没有**在超大库（10 万条以上）上做过实测，所以**不承诺**「多大都能用」。
2. **没有自动清理**：不按时间、不按条数自动删。删不删由用户决定。
   这也意味着：一直用下去，库会一直变大 —— 空间要自己盯。
3. **已实测的量级**：界面自检一次写入 120 条，打开显示 50 条 → 点「加载更早」→ 100 条，
   游标不重不漏。这是**当前唯一实测过的规模**，更大的规模写「未测」，不写「支持」。

如果哪天库大到打开变慢：先用「记录 → 备份」存一份，再用导出功能按会话导出 txt/JSON，
然后清掉不需要的旧会话。**不要手动删 `history.db`** —— 那是把全部记录一次性丢掉。

## 4. 备份与恢复（含边界）

**能做的**：

- 界面「记录 → 备份」→ `VACUUM INTO` 生成一致快照。**不要**在软件运行时直接复制 `history.db`，
  可能拷到半个事务。
- 恢复：先**完全退出**软件（托盘退出，不是关窗口），再用备份文件替换 `history.db`。

**做不到的**：

- 备份文件里**没有**设置和词表（见第 1 节）。
- 没有云端同步、没有自动定时备份。
- 向后降级不完整：v0.6.2 的库（schema v3）用 0.6.1 打开**不会报错**（启动日志记一条「schema 比本版本新」），
  但 0.6.1 写回时不写这 11 个新列 —— 它新写的事实卡**不会有**修改轨迹与「现在该怎么说」，
  老行里已存在的轨迹列也不会被它覆盖。**要保住轨迹就别降级。**

## 5. 从 0.6.1 升到 0.6.2 会怎样

| 项 | 结果 |
| --- | --- |
| 库结构 | v2 → **v3**：只 `ALTER TABLE facts ADD COLUMN`（11 列），不重建表、不删数据 |
| 已有记录（字幕 / 回复 / 分页游标） | 原样保留，条数与内容不变 |
| 已有事实卡 | 值、原话、已确认标志保留；新增的列对老数据为空 |
| 老数据的修改轨迹 | **没有**。0.6.1 之前 `confirmedAt` 与修改记录只存在内存里，从未写进库 —— 升级后不会凭空补出来，界面按「未记录」显示，不猜 |
| 设置与词表 | 保留（`settings.json` 不被安装包覆盖） |
| 需要手动做的 | 运行 `release/AI-Conversation-Copilot-Setup-0.6.2.exe` |

**更正上一版文档的一处错误**：《数据存储与备份-v0.6.1》写过「已确认的重点信息保留
（confirmedAt / 修改记录都在库里）」。这句话在 0.6.1 是**不成立**的 —— 那一版的 facts 表
没有这两列，确认时间与修改记录只活在内存里。v0.6.2 才把它们写进库。

升级前仍建议按老规矩来：**先备份，再装新版，装完核对条数**。

## 6. 什么情况下会丢

| 情况 | 会丢什么 | 说明 |
| --- | --- | --- |
| 正常退出 | 不丢 | 写队列会先排空 |
| 崩溃 / 强杀进程 | 可能丢**正在写的那一条 AI 回复** | 回复还没拿到数据库回执，进程就没了；这是 v0.6.1 已知代价，没修 |
| 手动「删除这段」/「清空全部」 | 按操作删 | 删完不会再被写回 |
| 卸载时勾了「删除应用数据」 | 全丢（记录 + 设置 + 词表） | 安装器选项，别误勾 |
| 直接删 `history.db` | 全部记录 | 没有回收站 |

## 7. 隐私边界（重申）

- 不保存原始音频，磁盘上没有录音文件。
- 数据库里**不放** API Key；Key 只在 `settings.json`，DPAPI 加密。
- 日志只记状态／错误码／字数／耗时，**不写**原文、译文、模型原始返回。
- 交付材料、截图、安装包里**不含**任何真实对话内容、密钥或录音。
