# 数据存储、备份与升级（v0.6.0）

## 1. 存在哪里

| 内容 | 位置 | 说明 |
| --- | --- | --- |
| 聊天记录 | `%APPDATA%\ai-conversation-copilot\history.db` | 真 SQLite（`node-sqlite3-wasm`） |
| 设置 | 同目录 `settings.json` | Key 用 DPAPI 加密后存在这里 |
| 日志 | 同目录 `logs\app.log` | 只记状态／错误码／字数／耗时 |
| 音频 | **不存** | 识别完就丢，磁盘上没有录音文件 |

卸载再装（不勾「删除数据」）与覆盖升级都不会清掉这些文件。

---

## 2. 库结构（schema v2）

三张表：`sessions` / `messages` / `facts`。

v1 → v2 只做**加列**，不重建表、不删数据：

| 表 | 新增列 | 用途 |
| --- | --- | --- |
| `sessions` | `comprehension` | 记下这段对话的「理解语言」 |
| `sessions` | `hint_system` | 记下这段对话用的读音提示体系 |
| `messages` | `hint_system` | 这条字幕的提示是汉字近音还是片假名 |
| `messages` | `hint_version` | 算这行提示时的算法版本（当前为 2） |
| `messages` | `comprehension` | 生成这条记录时的理解语言 |
| `messages` | `meaning` | 恢复历史时显示的释义 |

**为什么必须存「提示体系」**：用户把理解语言从中文改成日语之后，旧记录里的「哈喽」不能被当成片假名提示来理解。存住体系，打开旧记录显示的就是当时那行字，鼠标悬停会说明它是保存时的汉字近音。

升级用 `PRAGMA user_version` 当闸门，加列前先用 `PRAGMA table_info` 判存在，所以重复执行安全。实测：`schema upgraded v1 → v2` 之后旧数据条数不变、原文一字不差，`user_version = 2` 不会再升一遍。

一致性设置：`foreign_keys = ON`、`synchronous = FULL`、写批用 `BEGIN IMMEDIATE`。

> 一个必须说清的细节：这个 WASM 构建下 `journal_mode = WAL` **不生效**，实际退回 `delete` 回滚日志。回滚日志同样是原子的（异常退出不会留半个事务），但不是 WAL，写入也更慢 —— 文档里不写 WAL。

## 3. 分页与「加载更早」

- 游标用会话内的 `seq`，**不用时间戳**（同一毫秒可能有多条，用时间戳会重复或漏条）。
- 读法：`WHERE session_id = ? AND seq < ? ORDER BY seq DESC LIMIT n+1`。
- 界面点「加载更早」后，用前后 `scrollHeight` 的差值把滚动位置钉回原来那句。

实测：一个 120 条的会话打开后先显示 50 条，点一次「加载更早」变成 100 条，按钮仍在；1 万条数据的分页不重不漏。

**v0.5.0 的一个真实缺陷**：从库里读出来的消息转换时漏了 `seq` 字段，导致「加载更早」永远算不出游标 —— 第 51 条往前的内容在界面上点不出来（数据一直都在库里）。v0.6.0 已修，并有界面自检守着。

---

## 4. 什么时候写、什么时候显示「已保存」

- 唯一写入者是 `renderer/lib/history-sync.ts`，300 ms 防抖（含未完成识别时 900 ms）。
- 写入排队执行：上一批还没写完时，新的调用会**等**，不会直接返回失败让调用方清屏。
- 只有拿到主进程回执才显示「已保存」；失败显示「尚未保存」并指数退避重试（1s×2ⁿ，上限 30s）。
- 同一条消息用同一个 id 覆盖同一行：转写先到、译文后到、回复后到，都不会变成三条记录。
- 后到的更新**不会**把已经存好的 AI 回复／提示体系／理解语言冲成空（`excluded.x = '' THEN 保留旧值`）。
- 切会话前先等写队列排空；**没写成功就不切**，免得那几句话只留在内存里被下一次清屏扔掉。
- 删除这段记录 / 清空全部时**不 flush**，否则刚删的内容会被写回一个新会话里。

## 5. 备份与恢复

- **备份**：界面「记录 → 备份」用 `VACUUM INTO`，由 SQLite 自己生成一致快照。
  **不要**直接复制正在写入的 `history.db` —— 可能拷到半个事务。
- **恢复**：先完全退出软件，再用备份文件替换 `history.db`，重新打开。
- **导出**：单个会话导出 txt（500 条一批 append）、全库导出 JSON（`version: 2`）。导出文件里提示行的标签会跟着当时的体系走（写「片假名近音」而不是一律写「谐音」）。

---

## 6. 不设上限、不自动清理

- 数据库里**没有条数上限**，也不会按时间自动删。
- 界面上「同时显示多少条」是内存／渲染的限制，**不是**保存上限。
- 只有用户自己点「删除这段」或「清空全部」才会真的消失。

---

## 7. 隐私边界

- 不保存原始音频（没有录音文件）。
- 聊天数据库里**不放** API Key；Key 只在 `settings.json` 里，用 DPAPI 加密。
- 日志不写正文、不写译文、不写服务商回显的请求体。

---

## 8. 升级前建议做的一次性动作

1. 打开软件 → 记录 → **备份**，把 `history.db` 的快照存到别处（文件名带日期）。
2. 关掉软件，再装新版。
3. 打开新版 → 记录，确认条数与备份时一致。

如果升级后「记录」显示不可用：**不要删库**。先点「打开记录文件夹」把 `history.db` 复制一份，再看应用日志里的错误码。
