## 二、AI 工具用在哪些环节

| 环节 | 用法 | 怎么核 |
| --- | --- | --- |
| 代码骨架 | 让 AI 起草函数结构、类型定义、SQL | 逐行读，`npm run typecheck` + 真实数据库跑一遍 |
| 查 API | WASM SQLite 的行为、`Intl.Segmenter` 的可用性、Chromium 的 `inert` | 在目标 Electron 版本里实测，不采信描述 |
| 测试用例 | 让 AI 列出「应该测什么」的清单 | 清单只作参考，断言值全部来自程序真实输出 |
| 文案 | 界面提示语的初稿 | 按「能说出口、短、不承诺无法核验的事」逐句改 |
| 文档 | 结构化初稿 | 数字必须能在测试输出里找到，找不到就写「未执行」 |

## 三、被 AI 误导过的地方（留在文档里提醒自己）

1. **「53 条发音测试全绿」给了虚假安全感。**
   那 53 条只覆盖平假名词表。用户第一次试日语就撞上 `カメラ → kara`、`カタカナ → kaka`、`コーヒー → kohi`、`空港 → 空港`。测试数量不等于覆盖面 —— 这一版专门补了片假名、长音／促音／拗音、未知汉字三组用例（68 条）。

2. **提示词写长，7B 模型会返回裸 `{}`。**
   让模型同时输出原文、译文、近音、音标、音节时，字段一多就整段空。结论：细节交给代码兜底（本地引擎算读音），模型只做它擅长的部分。

3. **「找不到语音就退到第一个声音」看起来无害，实际是错的。**
   界面显示播放成功，用户听到的是英语腔念日语。现在缺语言就明确报 `TTS_LANG_UNAVAILABLE`。

4. **自检也会写错。**
   双面卡第一版断言读到 `inert = false`，原因是断言写在 Esc 关闭之后（那时已撤销）。不是功能坏了，是量错了时机。改成打开期间取值后为 `true`。

## 四、没做的事，以及为什么

- 没有做「全球所有语言」：目标语言 4 种，做透的方向 3 个。
- 没有做准确率统计：没有标注集，任何百分比都是编的。
- 没有做社区／账号／生词本：这一版只解决「听障 + 跨语言沟通」一条线。
- 没有请日语母语者核对读音、没有做听障使用者测试：见《目标使用者体验记录表-v0.6.0.md》。
