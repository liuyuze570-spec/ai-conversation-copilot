# 0.6.2 修复与验证

这一版只做一件事：**把「同一句确认话里出现两个不同的值」这类会让人当面说错话的问题修掉**，
顺手补上它连带的数据落盘缺口。没有做新功能，也没有改版式。

上一版（0.6.1）已经修好的部分（离线演示三方向译文、保存失败不丢回复、明确清空、
字号三类独立、读音词典与缩写）**保持不动**，本轮只是在它们上面加闸门。

---

## 一、最关键的一条：确认句的事实不一致

### 现象（用户实测）

- 原话片段：`15,000 dollars`
- 用户在确认卡里把「当前理解」改成 `16000美元`
- 点「帮我确认」得到：
  - 英文：`Just to confirm, 15,000 dollars. Is that right?`
  - 中文：`我理解的是16000美元，对吗？`

同一句确认话里两个地方说的是两个数。用户照着英文念，对方听到的还是 15,000。

### 根因

`buildConfirmSentence()` 里英文句子取 `fact.sourceText`（原话，永远不变），
中文释义取 `fact.value`（用户改过的当前理解）。只要用户改过值，两边必然分裂。

同时还有两个连带缺陷：

1. 过滤条件写的是 `!negated && certainty !== 'corrected'`。而模型那条路会把
   「不是三点，是四点」的**四点**标成 `corrected`（取更正后的值）—— 于是更正后的
   当前值被整条丢掉，确认句直接变空。
2. 句尾固定加 `. Is that right?`，遇到原话结尾本来就是 `p.m.` 就成了 `p.m.. Is that right?`。

### 改法

`src/shared/facts.ts` 不再「一半用原话、一半用改后值」，而是**两边都从当前理解出发**：

- 新增 `deriveSpoken(fact, target)`：算「这条**现在**该怎么说」。
  - 没改过值 → 原话（原话本来就是目标语言）。
  - 改过值且能机械推导 → 在**原话结构**上替换，保留原来的写法风格：
    - 时间点：`10:30` → `11:30`；`3 p.m.` → `10 a.m.`（小时和上下午一起改）
    - 星期：`Thursday` → `Friday`（中/英/日三种写法都认）
    - 数值：`15,000` → `16,000`（保留千分位写法）
    - 中文「万」写法：`1.5万` 与 `15000` 视为同一个数
  - **推不出来就不写半截句子**：换币种（`dollars` → `日元`）、换地点（`north gate` → `东门`）、
    改成「还没定」这类无法映射的内容，一律返回 `blocked`。
- 新增 `checkSentenceAgainstFacts(sentence, meaning, facts)`：第二道闸。
  - 句子里必须出现**改后的值**，不许出现**改前的值**（数字与星期都比）。
  - 释义里也必须出现改后的值。
  - 模型那条路同样过这道闸 —— 模型很自然会把原话里的 15,000 抄回去。
- 新增 `planConfirmSentence()`：返回 `{ ok, sentence, meaning, blocked, message }`。
  `buildConfirmSentence()` 保留原签名（能拼就返回、拼不出返回 null），只做薄包装。
- 句号叠加修掉（最后一段已以 `.` 结尾时，尾巴的 `.` 去掉）。

### 验收（本轮真跑）

| 场景 | 结果 |
| --- | --- |
| 15000 → 16000 | 英文 `16,000 dollars`、中文 `16000美元`，旧值不出现 |
| 周四 → 周五（周二被否定） | 英文 `Friday`、中文 `周五`；周二不进句子 |
| 10:30 → 11:30 | 英文 `11:30 a.m.`、中文 `11:30` |
| 3 p.m. → 上午10点 | 英文 `10 a.m.`（小时与上下午同步） |
| 15000美元 → 15000日元 | **拒绝生成**，提示「单位对不上，点改说法」 |
| 北门 → 东门 | **拒绝生成**，提示补一句外语说法 |
| 未修改 | 正常生成，数字与原话一致 |
| 用户补说法 `16,000 yen` | 采用用户说法；释义仍是当前理解 |
| 补的说法写成旧值 `15,000 dollars` | **拒绝生成**（数值闸） |
| 模型输出抄回旧值 | `checkSentenceAgainstFacts` 拦下 |

真界面证据（`docs/evidence-v0.6.2/v060-selfcheck.json` 第 `9-fact-confirm` 步，点的是真按钮）：

## 二、否定 / 更正 / 确认失效

| 问题 | 改法 |
| --- | --- |
| `factsForConfirm()` 只给「类型：值」两行，模型分不清哪个是被否掉的旧值 | 每行带**原话、状态、改前改后、现在该怎么说**；被否定的一行明确写「不许写进确认句」 |
| 模型提示固定要求中文释义（`chinese` 字段） | 提示词按**理解语言**生成，字段改为 `meaning`，并兼容旧的 `chinese` |
| 改了已确认的事实，`status` 仍是 `confirmed`、`confirmedAt` 还是上一次的时间 | 改值/改说法一律回到 `pending`、清空 `confirmedAt`，并在时间线里补一条 `unconfirmed` |
| 旧确认句在事实改动后仍留在屏幕上 | 任何内容改动都让 `draft` 作废（只点「确认」不清，避免刚生成的句子消失） |
| 在途请求回来时，可能把基于旧值的结果盖上来 | 事实 store 增加 `version`；请求发出时记下版本，回来时版本不符就丢弃 |

真界面证据：同上第 9 步的 `statusBefore: 已确认` → `statusAfter: 待确认`、
`draftClearedAfterEdit: true`。

## 三、事实卡的修改轨迹落盘

旧库只存 `value / source_text / certainty / confirmed / edited`。改前值、被否定关系、
确认时间、动作日志、「现在该怎么说」全都没进库 —— 重开记录只剩一个孤零零的值。

- `HistoryFact` 扩了 11 个字段：`sourceField / negated / originalValue / status /
  confirmedAt / log / spoken / spokenSource / comprehension / targetLanguage / hintSystem`。
- 数据库 `SCHEMA_VERSION` 2 → **3**，只加列、不改旧列、不重建表：
  `source_field, negated, original_value, status, confirmed_at, log, spoken,
  spoken_source, comprehension, target_language, hint_system`。
  老库升上来这些列为空，界面按「未记录」处理，不猜。
- `log` 以 JSON 存 `[{ at, action, from, to }]`，解析失败就当没有记录（不重建）。
- 删除要**真删**：`historySaveFacts` 新增 `removedIds`，只 upsert 不删的话，
  用户删掉的事实下次打开又回来了（和字幕的「明确清空」是同一个坑）。
- 事实卡有**单独的保存状态**（`factSaveState`），在卡片底部显示「已保存 / 尚未保存（重试）」。
  字幕存成功不会再掩盖事实卡写失败。

验证：`history-unit` L 组 18 条（写入 → 关库 → 重开 → 逐项比对，含 3 条轨迹、
否定标记、删除、空数组不误删）；跨进程重启检查从 15 项扩到 **24 项**，
其中 7 项专门比对修改轨迹。

## 四、个人词表：改完当前行不更新

**现象**：在字幕上点词改了读法、设置也存了，但屏幕上那一行还是旧读法。

**根因**：字幕行优先显示 `item.romanization`（当时保存的快照，历史记录要还原当时看到的字）。
`saveReading()` 只更新了设置里的词表，没有更新这一条字幕的保存值 —— 重算结果与保存值不一致，
按「不一样就显示保存的那行」的规则，屏幕继续显示旧读法。

**改法**：存完词表后，立刻用新词表重算这一句，并写回这条字幕的
`romanization / hintSystem / hintVersion`。这样当前行立即更新，同时「已保存的快照」
也跟着变成用户确认过的版本；没有编辑过的旧记录不受影响。

顺带把读音状态在界面上分清楚（`data-hint-origin`）：

| 界面状态 | 含义 | 会不会说成「已核对」 |
| --- | --- | --- |
| 词典命中（普通样式） | 词表收录的读法 | 不，提示里写「仍非母语者逐条核对」 |
| 规则近似（`approx`，虚点线 + 文字） | 规则拼的，没核对 | 明确写「没有人工核对」 |
| 未确定（虚线） | 没有可靠来源 | 不猜，标出来 |
| 我的读法（`origin=manual`，点线底） | **用户自己填的** | 写「不是专家核对」 |
| 人工核对过 | **本版没有任何真实核对记录，界面不出现这个状态** |

## 五、演示短句「明天 / 下周」

**现象**：`Tomorrow.` / `Next week.` / `See you tomorrow.` 三句都显示「明天 / 下周」。

**根因**：关键词兜底把命中的词用 ` / ` 连起来当译文。`tomorrow` 与 `week` 同时命中，
三句话自然得到同一串，用户分不清对方说的是明天还是下周。

**改法**：

1. 新增「整句短句」层（句子级，不是关键词级）：`Tomorrow.` → `明天。`、
   `Next week.` → `下周。`、`See you tomorrow.` → `明天见。`，
   日语方向 `明日。` / `来週。` / `また明日。`，英语方向 `明天。` → `Tomorrow.`。
2. 关键词兜底只在整句没命中时用，并且**明确标注**：
   `〔演示模式只认出关键词：明天、下周；整句译文没有预置，不猜〕原句`。
   这样一眼能看出这不是译文。
3. 完全没有预置时仍明说「没有这句的日语译文，不拿中文顶替」。

验证：`samples-unit` S9 共 16 条（含「三句译文互不相同」）。

## 六、音源通道在字幕产生时绑定

以前写库时才按当前设置反推音源，用户中途把「线上会议」切成「现场沟通」，
前面那些句子会被一起改写来源。现在：

- `ConversationItem` 增加 `audioSource`（system / mic）与 `comprehension`，
  **在字幕产生那一刻**打上；
- 写库用 `item.audioSource ?? 按设置回退`（旧数据仍能读）。

## 七、这一版**没有**做的事（不要当成已实现）

- **没有接真实模型验证确认句**：本机没有可用的 API Key / 余额。
  模型那条路的代码（提示词、两道闸）写好了，但「真实模型会给出什么样的句子」
  本轮**没有实测**。演示模式走的是本地拼句，已实测。
- **没有真人体验**：听障使用者 0 人，母语者读音核对 0 条（清单与记录表已备好）。
- **没有真实语音链路**：识别 / 翻译 / 朗读仍依赖服务商，未端到端跑通（HTTP 402）。
- **没有干净机安装、没有代码签名、10 万条以上大库未测**。
- 读音引擎本版未改动，`读音核对清单-v0.6.1` 仍然适用。
