## 2. 真实翻译（本地 Opus-MT，进程内 ONNX）

模型：`Xenova/opus-mt-en-zh` 量化 ONNX，encoder 52,899,742 字节 + decoder 60,212,804 字节，
合计 107MB。beam=4（模型自带 `num_beams`），长度惩罚 1.0，贪心可复现（同一输入两次同结果）。

| 英文原文 | 实际译文 | 耗时 |
|---|---|---|
| Please send the report by 3 p.m. tomorrow. | 请在明天下午3时前将报告发送。 | 615–876ms |
| The meeting is not on Tuesday. It has moved to Thursday at 10:30 a.m. | 会议不是在星期二举行,而是在上午10时30分改为星期四举行。 | 788–854ms |
| The budget is fifteen thousand, not fifty thousand. | 预算是一万五千元,不是五万元 | 638–866ms |
| I will bring the blue folder to the office at 4.15 p.m. on Friday. | 星期五下午4时15分,我将把蓝文件夹带回办公室。 | 761–765ms |
| The train leaves at seven forty-five from platform two.（**新句，未预置**） | 列车从2号平台745出发 | 521–565ms |
| The delivery is not on Friday. It will arrive next Monday at 9 a.m.（**新句，未预置**） | 星期五不送货,下星期一上午9时到 | 594–722ms |

**模型加载**：845ms（首次），启动阶段预热一次，第一个用户不用等。
**并发**：单进程内串行（一把锁），同一时刻只跑一个翻译。

### 这一组里真实存在的问题

`seven forty-five` 被识别成 `745`，译文成了「745出发」——数字对，但**时间形式丢了**，
读者可能读成「七百四十五」。我给识别加了 `initial_prompt` 提示书写格式，
`9am → 9 a.m.` 修好了，`745` 没修好。不猜着改的原因是：`room 745` 同样会被改写错，
把「房间 745」改成「7:45」比不修更危险。**这一条列为已知缺陷**，界面上的对策是
原句始终显示、事实卡允许手工改值，不替用户下结论。

## 6. 边界与失败路径（本次实测）

| 场景 | 实际返回 | 判断 |
|---|---|---|
| 文本 2100 字 | `TOO_LARGE`「文本超过 2000 字」 | 预期 |
| 非英语方向（zh→en） | `BAD_REQUEST`「这版只做英语 → 中文」 | 预期，不假装支持 |
| 一分钟内第 28 次请求 | `RATE_LIMITED` | 限流生效（30 次/分） |
| 不带会话 Cookie 直接调接口 | `SESSION_REQUIRED` | 接口不裸奔 |
| 总开关 `COPILOT_REAL_DISABLED=1` + 预置内句子 | `mode=mock`，0ms | 走预置，不跑模型 |
| 同上 + 预置外句子 | `NO_PRESET`「演示模式下没有这句的预置译文」 | 不拿样例冒充 |
| 同上 + 上传音频 | `NOT_CONFIGURED`「服务端没有可用的识别能力」 | 明确拒绝，不编字幕 |
| 正常实例 + 预置外句子 | `mode=local-onnx`，真实译文 | 真实路径不受影响 |

### 顺手修掉的一个真 bug

第一次测总开关时发现：`COPILOT_REAL_DISABLED=1` 下 `/api/health` 回报
`mode=mock / real=false`，但 `/api/translate` **仍然调了真实模型**，
返回 `mode=local-onnx`。原因是那处判断写成了 `if ... : pass`，什么也没做。

这种不一致比没有开关更危险：运维看到「已关闭」以为停了，费用和隐私承诺都在继续。
现在统一由 `backend_or_none()` 选路，三个接口（translate / transcribe / reply）
都强制只走 mock 那一路，未命中就明确报错。改动后重跑上表 3 行，行为一致。

**没测过的**（不要当成已通过）：无效 Key、上游超时、断网后恢复、麦克风权限被拒、
暂停/取消在途请求、访客配额用尽（40 次/会话）、临时会话开关、网页刷新与离开、Safari。

### 10.2 问题一：英文单个的数词读不出来 → 假警报 + 漏检

`scanNumbers()` 原来只认「数词 + hundred/thousand…」，于是：

| 输入 | 修复前 | 后果 |
|---|---|---|
| `platform two` | `[]` | 译文写「2 号站台」被判「原文没有 2」——假警报 |
| `three people` | `[]` | 译文写「两个人」**完全漏检** |
| `forty-five` | `[]` | `745` 的成因查不出来 |
| `one hundred and fifty` | `[100, 150]` | 一句话被当成两个数，多报一条「缺了 100」 |

修复后（`src/shared/numeric-check.ts`）：补「单独数词 / 连字符 / `a hundred`」三条规则，
`one` 当代词时（`no one` / `one of them`）不算数；前一条规则吃掉的 span 不再重复计数；
原文的 `7`+`45` 被译文合成 `745` 时不再重复报两条缺失。

同一句的警报从 2 条降为 1 条，且指向真正的问题：

```
原文  The train leaves at seven forty-five from platform two.
译文  列车从2号站台起 745离开
修复前  译文里的「2」在原文中找不到；译文里的「745」在原文中找不到
修复后  译文里的「745」在原文中找不到（原文是 seven = 7 / forty-five = 45）
```

新增回归：`C12–C18`（数词扫描）、`A12–A16`（误报/漏报），一致性套件 61 → **80 条**。

### 10.3 问题二：中文确认句的释义里夹着英文

`planConfirmSentence()` 原来把 `fact.value` 原样拼进释义，实际输出是：

```
确认句  Just to confirm, twelve thousand. Is that right?
释义    我理解的是twelve thousand，对吗？
```

最该让用户确认的那一段，反而是他读不懂的英文。修复：把早已写好却一直没被调用的
`toChineseSpeech()` 接进释义（只在值里含拉丁字母时转换；转换后仍带英文、或数值对不上
就整条放弃），顺带修掉 `next Monday → next 周一`。

```
释义  我理解的是下午2点、周五、一万二千，对吗？
```

英文句子保持英文（那是要念给对方听的），只有释义走中文。新增回归 `M1–M8`，
确认句套件 78 → **86 条**。
