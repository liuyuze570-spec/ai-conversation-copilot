# 目标使用者体验记录表（v0.6.0）

## 一、结论先说

**目标使用者（听障者）的体验测试：未执行。**

这一版没有请到听障使用者本人做任务测试，也没有做读屏软件实读。下面写清楚：为什么没做、替代做了哪些、以及下一步怎么做才是最省时间的。

请不要把本文件当成「用户验证过的证据」。

---

## 二、为什么没做

| 原因 | 说明 |
| --- | --- |
| 没有可协调的测试对象 | 本轮开发周期内没有联系到愿意配合的听障使用者 |
| 不编造 | 与其写「用户反馈良好」，不如写「没测」 |
| 演示链路不完整 | 本机缺少英语 TTS 语音、服务商余额不足，真实链路端到端跑不通；在这种情况下让使用者试用，得到的反馈会混杂在「软件坏了」里，没有诊断价值 |

---

## 三、替代做了哪些（不能替代，但能排除明显问题）

| 做法 | 结果 |
| --- | --- |
| 用键盘走全流程（Tab / Shift+Tab / Esc） | 双面卡打开时焦点锁在卡内、背景 `inert` 生效、Esc 关闭后焦点回入口按钮（自检步骤 5 实测 `true`） |
| 检查提示是否会「骗人」 | 词典外的汉字标「未确定」，不显示编造的读音；句子状态变成「部分未确定」 |
| 检查朗读会不会「假装成功」 | 缺目标语言语音时明确报错（本机只有中文语音，实测显示「缺少 en-US 语音｜系统现有 1 种语言的声音（zh）」） |
| 检查字号是否真的独立 | 三类各自调到 12–64，互不推动；15 / 23 这种中间值不被迁移改写（45 条断言） |
| 模拟任务的三条样例句 | 请再说一遍 / 改期到周四 10:30 / 金额 15000 不是 50000 —— 作为后续真实测试的任务脚本 |

---

## 四、下一步怎么测（可直接照着做）

**对象**：3 位有英语沟通需求的听障使用者（佩戴助听器或人工耳蜗，能读中文）。

**任务脚本**（每条约 10 分钟，共 30 分钟）：

1. 让对方再说一遍：字幕里有你听不懂的一句，请让它生成一句「请再说一遍」并念出来。
2. 改期：字幕说「会议在周二」，实际是「周四上午 10 点半」。请用软件确认时间。
3. 金额：15000 与 50000 的差别。请确认金额。

**记录什么**（每条只要三样）：

- 在哪一步停住了（第几秒、点了什么）
- 他有没有**不相信**屏幕上的内容（信任度问题往往比可用性更致命）
- 他有没有绕过软件（比如直接拿手机打字）—— 绕过说明这一步没帮上忙

**不要问的问题**：「你觉得好用吗」「界面好看吗」。答案没有信息量。

**判定标准（先写下来，避免事后找理由）**：

- 3 人里至少 2 人能在 60 秒内完成第 2、3 条任务 → 核心价值成立
- 出现「看不懂提示在标什么」→ 提示的呈现方式要改，不是读音算法的问题

---

## 五、已知会影响体验的问题（测之前就知道的）

1. **回复要等 7–9 秒**（非流式），尾部会更慢。真实对话里这个延迟会被感知为「它没在听我」。
2. **本机没有英语 TTS 语音**，朗读功能在这台机器上不可用（会明确报错）。
3. **字号调到 40px 以上**会进入极简底栏，只能靠「更多」回到其它功能 —— 大字号用户要多点一次。
4. **提示是近似**，念出来对方可能需要再确认一次。这是这一版的能力边界，不是缺陷。
