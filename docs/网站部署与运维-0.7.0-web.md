### 会话出问题时怎么查（0.7.0-web.3 起）

`/api/health` 的 `diag` 是专门为这件事加的，不含 sid / 密钥 / 正文：

```bash
curl -s "https://<域名>/api/health?sharecode=<码>" | python -c "import sys,json;print(json.load(sys.stdin)['diag'])"
```

- `boot` 变了 → 服务端换过进程（部署、重启、内存回收），页面手上的会话必然失效；
- `uptime_s` 很小（几十秒）→ 刚重启过，这时访客第一次提交可能撞上 `SESSION_REQUIRED`；
- `sessions` 持续增长不回落 → 会话没有被清理（只有 TTL 到期才会删），长时间运行要留意内存；
- 前后两次请求 `boot` 不同 → 请求被不同实例接走（当前部署是单实例，出现即异常）。

客户端现在会自愈：`SESSION_REQUIRED` 带 `recoverable:true`，前端重建一次会话并重试一次，
最多一次；再失败就显示「重试一次」按钮并保留输入。要复现和验收这套行为，跑
`node webapp/e2e/session-recovery.mjs`（本地 18 项）或带 `WEB_BASE=…` 跑线上 8 项。

## 4. 回滚

服务不写数据库（会话只在内存），所以回滚**不涉及数据迁移**，只要把代码退回上一版
再发布一次。

```bash
cd "F:/3D打印Rhino 7.0/2026-09-30-23-01-15"
git log --oneline            # ca56dff 是 0.7.0-web.1 的基线
git status --short           # 先看清哪些改动没提交
# 回滚到基线（示例，执行前先备份当前改动）
git stash push -u -m "回滚前存档"
# 重新构建前端 → 发布
cd webapp/web && npm run build
```

发布后核对顺序：`/api/health` 的 `version` → 首页可见的徽标（「本地翻译模型（真实翻译）」）
→ 随便翻一句新句子看 `mode` 是否为 `local-onnx`。

> 这套回滚**流程**基于本机 git 与重新发布，**没有在线上实际演练过**。
> 路演前如果要保证可回滚，建议先发布一次再回滚一次，把两次的 health 截图存下来。

## 5. 关闭真实调用（应急开关）

开关是环境变量 `COPILOT_REAL_DISABLED=1`。三个接口（translate / transcribe / reply）
统一由 `backend_or_none()` 选路，置 1 后**只返回预置结果**，未命中预置就明确报错，
不会偷跑模型。

**已实测（本机）**：

| 操作 | 结果 |
|---|---|
| `COPILOT_REAL_DISABLED=1` + 预置内句子 | `mode=mock`，0ms，界面标「预置演示」 |
| 同上 + 预置外句子 | `NO_PRESET`「演示模式下没有这句的预置译文」 |
| 同上 + 上传音频 | `NOT_CONFIGURED`「服务端没有可用的识别能力」 |
| 同上 + `GET /api/health` | `real` 三项全 `false`，`mode` 全 `mock` |

**未实测**：线上平台是否支持在发布时注入环境变量。我没有在平台上设过。
所以线上的应急手段目前只有一条我确定能做到的：**把分享链接下线**（平台的应用管理里操作），
链接立即失效，比「关掉真实调用但服务还在跑」更彻底。

## 6. 限额与配额（线上 `health.limits` 原样）

| 项 | 值 | 说明 |
|---|---|---|
| `max_chars` | 2000 | 单次文本上限，超了返回 `TOO_LARGE` |
| `max_audio_mb` | 8.0 | 上传音频大小上限 |
| `max_audio_seconds` | 60 | **先探时长再推理**，超长直接拒，不浪费一次识别 |
| `quota_translate` | 40 / 会话 | 每个访客会话 |
| `quota_transcribe` | 10 / 会话 | 识别比翻译贵，配额单独扣，不互相偷 |
| `quota_reply` | 15 / 会话 | 回复单独扣（旧代码的 `else` 分支会偷识别额度，已改成 `elif`） |
| 频率 | 30 次 / 分钟 | 超了 `RATE_LIMITED` |

会话靠 HttpOnly Cookie 标识，服务重启即清空（内存字典）。

## 8. 改代码后必须做的事

1. `cd webapp/web && npm run build` —— 服务端托管的是前端产物，不重建就还是旧页面；
2. `npm run typecheck`（根目录）—— 共享模块被桌面端和网页端同时引用；
3. `npm run test:unit` —— 15 套 / 1157 条，改共享层必跑；
4. 起本机服务后跑 `node webapp/e2e/probe.mjs`（24 项）与 `node webapp/e2e/run.mjs`（8 步）；
5. 同步到发布目录，再发布（见下）；
6. 发布后在**另一台设备**上重新走一遍：首页、翻译、录音识别、确认句、大字卡。

### 重新发布（2026-11-09 实际走过的流程）

发布源是 `F:\copilot-deploy\app`，布局固定为：

```
run.py                  # 自己读 PORT，uvicorn 起 server.app
server/                 # app.py / engine_*.py / requirements.txt / models/
web/app/                # 前端产物（index.html + assets/）
mt/models/              # ONNX 翻译模型
```

为什么前端放在 `web/app` 而不是 `web/dist`：发布平台打包时会排除构建产物目录，
`dist` 传不上去；`app.py` 的 `_resolve_web_dist()` 认 `../web/dist` 和 `../web/app` 两个名字。

同步步骤（发布前必须做完，且核对指纹）：

```bash
# 1. 构建
cd "F:/3D打印Rhino 7.0/2026-09-30-23-01-15/webapp/web" && npm run build
# 2. 覆盖前端产物
rm -rf "F:/copilot-deploy/app/web/app" && mkdir -p "F:/copilot-deploy/app/web/app"
cp -r dist/index.html dist/assets "F:/copilot-deploy/app/web/app/"
# 3. 同步服务端代码（有改动时）
#    web.9 改了 app.py / engine_asr.py；切片纯逻辑在 src/shared/caption-pipeline.ts，
#    由 Vite 打进第 2 步的前端产物，不需要单独往 server/ 里拷。
#    web.10 同理：只改 VERSION/BUILD_ID（app.py）+ src/shared/reply-plan.ts、
#    caption-pipeline.ts 与 webapp/web/src/{state,tabAudio,TabAudioPanel,App}.tsx，
#    全部由第 2 步的前端产物带上；服务端文件清单没有新增，但 app.py 版本号必须同步。
#    ⚠ 2026-11-09 16:34：web.10 只在本机 8903 验证，本轮**故意没有执行本段同步**，
#    `F:/copilot-deploy/app` 仍是 web.9（= 线上），保持随时可回退的状态。
cd "../server" && cp app.py engine_asr.py engine_mt.py engine_mt_onnx.py \
  engine_mt_multi.py engine_reply.py phrasebook.py feedback_store.py requirements.txt \
  "F:/copilot-deploy/app/server/"
# 3.0 反馈库（web.8 起）：运行时会在 server/data/ 下建 SQLite 文件。
#     发布前不要删这个目录 —— 删了等于把用户反馈清空。
mkdir -p "F:/copilot-deploy/app/server/data"
#     可选：把本地已收到的反馈库一起带上（第一次部署时目录为空即可）
#     cp ../server/data/feedback.sqlite3 "F:/copilot-deploy/app/server/data/"
# 3.1 多语言模型（第一次部署或模型更新时才需要；约 340MB）
cp -r ../mt/models/Xenova/Xenova__opus-mt-ja-en \
      ../mt/models/Xenova/Xenova__opus-mt-ko-en \
      ../mt/models/Xenova/Xenova__opus-mt-ru-en \
      "F:/copilot-deploy/app/mt/models/Xenova/"
# 4. 本地先验证这个布局能跑（部署目录里没有 venv，用源码树那个）
cd "F:/copilot-deploy/app" && PORT=8899 \
  "F:/3D打印Rhino 7.0/2026-09-30-23-01-15/webapp/server/.venv/Scripts/python.exe" run.py
curl -s --noproxy '*' http://127.0.0.1:8899/ | grep -o 'assets/[a-zA-Z0-9._-]*'
curl -s --noproxy '*' http://127.0.0.1:8899/api/health | head -c 400   # 看 version / languages
# web.9 起还要看新限制确实生效：audio_budget_seconds / segment_max_seconds /
# asr_concurrency / rate_per_min（缺了说明服务端代码没同步）
curl -s --noproxy '*' http://127.0.0.1:8899/api/health | grep -o 'audio_budget_seconds[^,]*'
# web.8 起还要验反馈接口确实挂上了（storage 必须是 sqlite-file，不是 unavailable）
curl -s --noproxy '*' http://127.0.0.1:8899/api/feedback/config | head -c 300
```

用 curl 手工测接口时要先建会话，且**必须用 `token` 那个字段**：

```bash
TOK=$(curl -s -X POST "http://127.0.0.1:8899/api/session" \
      | python -c "import sys,json;print(json.load(sys.stdin)['token'])" | tr -d '\r\n')
curl -s -X POST "http://127.0.0.1:8899/api/translate" \
     -H "Content-Type: application/json" -H "x-session-id: $TOK" \
     -d '{"text":"hellow","source_language":"en"}'
```

`/api/session` 返回两个 ID，容易拿错：`session_id` 只有 8 位，**是给人看日志用的**，
不是凭据；`token` 才是完整会话号。拿 `session_id` 去调会一直得到
`SESSION_REQUIRED / reason=unknown`，看起来像「会话随机失效」，实际是自己传错了
（本轮排查时就绕了一圈）。另外 Windows 上 `python -c print` 会带回车，要 `tr -d '\r'`，
否则请求头里混进 `\r` 一样对不上。

发布时**必须显式给启动命令**，否则平台默认跑 `main.py`：

```
startCmd = "python run.py"      # 实测：不传会报 /workspace/main.py: No such file
```

第一次这么发布时踩过一次：默认启动命令让服务没起来，那一次**原分享链接短暂打不开**，
补上 `startCmd` 重发后恢复。所以发布参数要写进本文件，不要靠记忆。

**发布前先升版本号**（`VERSION` / `BUILD_ID`，见 `webapp/server/app.py` 顶部）。
不升就发，线上 `/api/health` 与本地同号，事后无法从版本判断「到底发上去了没有」——
只能靠比对行为，很容易误判成发布失败。本轮就吃过一次：代码发上去了但号没动，
后面又补了一次 web.6 重发。

然后调用发布（同一目录 = 同一个应用，分享链接不变），最后核对线上首页指纹与本地一致。

## 9. 不能宣称的

- 「web.10 已上线」：**没有**。`0.7.0-web.10` 只在本地 8903 跑过，公网仍是
  `0.7.0-web.9`，部署副本也保持 web.9 未同步；线上 P3 验收（55 项）未做。
  用户明确要求发布后才能覆盖 live link，见 `docs/回退说明-0.7.0-web.md`。
- 「AI 自动回复已实现」：**没有**。`COPILOT_LLM_*` 未配置，`health.mode.reply=mock`、
  `real.reply=false`。web.10 只是把固定三句换成**按内容生成的本地规则**，
  界面标「不是模型」；配置三个环境变量后 `/api/reply` 才会返回真模型结果，
  届时前端自动换成「AI 建议」。路径存在 ≠ 已接通，见报告第 18.1 节。
- 「云端模型效果」：线上没有 Key，`reply` 一直是模板。
- 「高可用 / 自动扩缩容」：单实例单进程，模型常驻内存约 875MB。
- 「线上重启/环境变量注入已验证」：没有。
- 「线上回滚演练过」：没有。
- 「web.8 单独上线过」：**没有**。web.8 只在 8899 与备份副本；2026-11-09 15:41
  直接从 web.7 一次性发布到 **`0.7.0-web.9`**（含 web.8 的 P0/P1 改动）。
- 「线上已验收」：web.9 线上 19 项 + P0 34 步 + P1 32 步 + P2 52 项全部通过，
  详见 `docs/网站测试报告-0.7.0-web.md` 第 17 节；**不等于**准确率、真人授权、
  四平台兼容也通过。
- 「线上标签页音频翻译已验证」：**只验了下游链路**。线上用合成语音注入真实
  MediaStream，切片 → 识别 → 翻译 → 字幕跑通；真人点选视频标签页、取消授权、
  关闭标签页都未自动化验证；抖音网页版 / 腾讯视频 / 爱奇艺全部未测试；
  B 站只有 2026-11-09 一张用户现场截图（非助手实测，不标已支持）；受保护内容不绕过。
- 「网页端实时字幕识别准确」：**没有**。本地合成语音演示中 3 条字幕有 2 条识别错误
  （固定 3 秒硬切片切在句中），详见 `docs/翻译其他网页视频-P2演示与兼容表.md` 第 2.2 节。
- 「反馈在线上持久保存」：**只验证了一半**。线上提交拿编号、刷新页面 / 新会话后按凭证
  仍可查已实测（`FB-20261109-DF08E5`）；**服务重启或重新部署后仍可查未验证**。
  且部署目录含 `server/data/feedback.sqlite3`，重新发布时它随源码上传，可能覆盖线上
  已收到的反馈；需要持久卷 / 外置数据库方案并实测。
