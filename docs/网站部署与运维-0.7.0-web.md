### 会话出问题时怎么查（0.7.0-web.3 起）

`/api/health` 的 `diag` 是专门为这件事加的，不含 sid / 密钥 / 正文：

```bash
curl -s "https://<域名>/api/health?sharecode=<码>" | python -c "import sys,json;print(json.load(sys.stdin)['diag'])"
```

- `boot` 变了 → 服务端换过进程（部署、重启、内存回收），页面手上的会话必然失效；
- `uptime_s` 很小（几十秒）→ 刚重启过，这时访客第一次提交可能撞上 `SESSION_REQUIRED`；
- `sessions` 持续增长不回落 → 会话没有被清理（只有 TTL 到期才会删），长时间运行要留意内存；
- 前后两次请求 `boot` 不同 → 请求被不同实例接走（当前部署是单实例，出现即异常）。

客户端现在会自愈：`SESSION_REQUIRED` 带 `recoverable:true`，前端重建一次会话并重试一次，
最多一次；再失败就显示「重试一次」按钮并保留输入。要复现和验收这套行为，跑
`node webapp/e2e/session-recovery.mjs`（本地 18 项）或带 `WEB_BASE=…` 跑线上 8 项。

## 2. 健康检查

```bash
# 先拿分享码换 Cookie，再查健康（不带 Cookie 会被 403 挡在链接校验那一步）
curl -s -c /tmp/pub.txt \
  "https://en-zh-caption-helper.app.workbuddy.host/?sharecode=X3A6YY6GQH" > /dev/null

  "https://en-zh-caption-helper.app.workbuddy.host/api/health"
```

判读规则：

- `ok: true` —— 进程活着；
- `real.translate: true` 且 `mode.translate: local-onnx` —— 走的是真实本地模型；

## 3. 重启

**本机**（唯一我亲手重启过的环境）：

```bash
# 停：Ctrl+C，或结束占用 8000 的进程
# 起：
cd webapp/server && NO_PROXY=127.0.0.1,localhost \
  ./.venv/Scripts/python.exe -m uvicorn app:app --host 127.0.0.1 --port 8000
```

启动日志里应能看到两行预热：`mt warmup {... load_ms: 7xx, warmup_ms: 5xx}` 与
`Application startup complete`。预热是故意的——第一个用户不该等模型加载。

**线上**：平台侧有没有单独的重启按钮，我没有实测过，不写猜测路径。
我能确认的是：**重新发布一次会重建实例**，发布后 `/api/health` 的 `version`
和前端指纹都会变，可以据此判断新实例是否起来了。

## 4. 回滚

服务不写数据库（会话只在内存），所以回滚**不涉及数据迁移**，只要把代码退回上一版
再发布一次。

```bash
cd "F:/3D打印Rhino 7.0/2026-09-30-23-01-15"
git log --oneline            # ca56dff 是 0.7.0-web.1 的基线
git status --short           # 先看清哪些改动没提交
# 回滚到基线（示例，执行前先备份当前改动）
git stash push -u -m "回滚前存档"
# 重新构建前端 → 发布
cd webapp/web && npm run build
```

发布后核对顺序：`/api/health` 的 `version` → 首页可见的徽标（「本地翻译模型（真实翻译）」）
→ 随便翻一句新句子看 `mode` 是否为 `local-onnx`。

> 这套回滚**流程**基于本机 git 与重新发布，**没有在线上实际演练过**。
> 路演前如果要保证可回滚，建议先发布一次再回滚一次，把两次的 health 截图存下来。

## 5. 关闭真实调用（应急开关）

开关是环境变量 `COPILOT_REAL_DISABLED=1`。三个接口（translate / transcribe / reply）
统一由 `backend_or_none()` 选路，置 1 后**只返回预置结果**，未命中预置就明确报错，
不会偷跑模型。

**已实测（本机）**：

| 操作 | 结果 |
|---|---|
| `COPILOT_REAL_DISABLED=1` + 预置内句子 | `mode=mock`，0ms，界面标「预置演示」 |
| 同上 + 预置外句子 | `NO_PRESET`「演示模式下没有这句的预置译文」 |
| 同上 + 上传音频 | `NOT_CONFIGURED`「服务端没有可用的识别能力」 |
| 同上 + `GET /api/health` | `real` 三项全 `false`，`mode` 全 `mock` |

**未实测**：线上平台是否支持在发布时注入环境变量。我没有在平台上设过。
所以线上的应急手段目前只有一条我确定能做到的：**把分享链接下线**（平台的应用管理里操作），
链接立即失效，比「关掉真实调用但服务还在跑」更彻底。

## 6. 限额与配额（线上 `health.limits` 原样）

| 项 | 值 | 说明 |
|---|---|---|
| `max_chars` | 2000 | 单次文本上限，超了返回 `TOO_LARGE` |
| `max_audio_mb` | 8.0 | 上传音频大小上限 |
| `max_audio_seconds` | 60 | **先探时长再推理**，超长直接拒，不浪费一次识别 |
| `quota_translate` | 40 / 会话 | 每个访客会话 |
| `quota_transcribe` | 10 / 会话 | 识别比翻译贵，配额单独扣，不互相偷 |
| `quota_reply` | 15 / 会话 | 回复单独扣（旧代码的 `else` 分支会偷识别额度，已改成 `elif`） |
| 频率 | 30 次 / 分钟 | 超了 `RATE_LIMITED` |

会话靠 HttpOnly Cookie 标识，服务重启即清空（内存字典）。

## 7. 上传的音频去哪了

上传的字节先落临时文件（`tempfile.NamedTemporaryFile`），识别完在 `finally` 里
`unlink`，异常路径也删。**不落库、不写磁盘长期目录、不进日志**。

日志（`app.log` / stdout）只记：请求 id、路径、状态码、耗时、错误类型、字数；
**不记正文、不记译文**。

## 8. 改代码后必须做的事

1. `cd webapp/web && npm run build` —— 服务端托管的是前端产物，不重建就还是旧页面；
2. `npm run typecheck`（根目录）—— 共享模块被桌面端和网页端同时引用；
3. `npm run test:unit` —— 15 套 / 1157 条，改共享层必跑；
4. 起本机服务后跑 `node webapp/e2e/probe.mjs`（24 项）与 `node webapp/e2e/run.mjs`（8 步）；
5. 同步到发布目录，再发布（见下）；
6. 发布后在**另一台设备**上重新走一遍：首页、翻译、录音识别、确认句、大字卡。

### 重新发布（2026-11-09 实际走过的流程）

发布源是 `F:\copilot-deploy\app`，布局固定为：

```
run.py                  # 自己读 PORT，uvicorn 起 server.app
server/                 # app.py / engine_*.py / requirements.txt / models/
web/app/                # 前端产物（index.html + assets/）
mt/models/              # ONNX 翻译模型
```

为什么前端放在 `web/app` 而不是 `web/dist`：发布平台打包时会排除构建产物目录，
`dist` 传不上去；`app.py` 的 `_resolve_web_dist()` 认 `../web/dist` 和 `../web/app` 两个名字。

同步步骤（发布前必须做完，且核对指纹）：

```bash
# 1. 构建
cd "F:/3D打印Rhino 7.0/2026-09-30-23-01-15/webapp/web" && npm run build
# 2. 覆盖前端产物
rm -rf "F:/copilot-deploy/app/web/app" && mkdir -p "F:/copilot-deploy/app/web/app"
cp -r dist/index.html dist/assets "F:/copilot-deploy/app/web/app/"
# 3. 同步服务端代码（有改动时）
cd "../server" && cp app.py engine_asr.py engine_mt.py engine_mt_onnx.py engine_reply.py \
  requirements.txt "F:/copilot-deploy/app/server/"
# 4. 本地先验证这个布局能跑
cd "F:/copilot-deploy/app" && PORT=8899 ../.venv/Scripts/python.exe run.py
curl -s --noproxy '*' http://127.0.0.1:8899/ | grep -o 'assets/[a-zA-Z0-9._-]*'
```

然后调用发布（同一目录 = 同一个应用，分享链接不变），最后核对线上首页指纹与本地一致。
