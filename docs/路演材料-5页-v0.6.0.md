# 路演材料（5 页）· v0.6.0

> 每页给的是**台上要说的句子**，不是功能清单。

## 第 1 页 · 问题：这不是「翻译不准」，是「说不出」

**一句话**：听障者戴着助听器能听见声音，但在英语会议里，他卡住的地方往往不是听不懂，而是**没法开口、也不敢确认自己听对了没有**。

三个真实的卡点（按出现频率排）：

1. **请对方再说一遍**——说不出口，只能点头。
2. **改期**——「会议不是周二，是周四上午 10 点半」，听到的是周二，不敢确认。
3. **金额**——「15000 不是 50000」，差一个零，签字前才发现。

现有工具解决的是「把话变成字」。我们的判断是：**光有字幕不够**，还得让人能（a）看懂、（b）念出来、（c）确认关键数字。

**所以这个产品做的是一条完整的链**：系统声音 → 外语原文 + 你看得懂的译文 → 你能照着念出来的读音提示 → 一句能直接说出去的回复。

## 第 2 页 · 做法：把「谁在听、想说什么、怎么标音」拆成四件事

上一版有一个我们自己撞上的错误：一个日语使用者装上软件，看到的是一行汉字谐音——对他毫无意义，但软件觉得「已经给了注音」。

这一版把原来写死的三件套（中文界面 + 中文译文 + 汉字近音）拆成**四个独立设置**：

| 设置 | 例子 |
| --- | --- |
| 界面语言 | 简体中文（本版固定） |
| 你理解的语言 | 中文 / 日本語 / English |
| 我想说的语言 | 英语 / 日语 |
| 读音提示 | 汉字近音 `哈喽` / 片假名 `ハロー` / 罗马字 `konnichiwa` |

**做透的三个方向**：中文 → 英语（汉字近音）、日本語 → 英語（片假名）、English → 日本語（罗马字）。其余组合能选，但界面上写明「不在实测清单内，可用但未核对」。

三件让「能说出口」真的成立的交互：

1. **点词看读音**：点原文任意一个词，下面那行提示里对应的那一段同时亮起来——「这串音对应的是哪个词」不用自己数。
2. **慢速 / 分句**：按真实词边界一段一段念，不是把句子按字数均匀切开。
3. **双面卡**：自己那面看释义和读音提示，翻过去是给对方看的一句大字原文 + 手动朗读键。**不自动朗读、不自动发送。**

一个诚实的取舍：读音提示是**本地规则引擎**算的（不联网、不花钱），打不到的词标「未确定」画虚线，**不猜**。空着比错着安全。

## 第 3 页 · 现场演示（8 分钟里跑完这三件事）

演示环境：本机、演示模式（不碰声卡、不调用付费接口），三条预置样例。

| # | 场景 | 台上做什么 | 观众看到什么 |
| --- | --- | --- | --- |
| 1 | 请再说一遍 | 点「我没听清」 | 一句可以直接念的英语 + 逐词读音提示 |
| 2 | 会议不是周二，改成周四上午 10:30 | 看字幕 + 打开「重点信息」勾选时间点「确认」 | 生成一句「我理解的是周四上午 10 点半，对吗？」 |
| 3 | 金额是 15000 不是 50000 | 同上，勾选金额 | 确认句里只有 15000，不会被写成 50000 |

中间穿插两个 15 秒的小动作：

- **点词**：点字幕里 `Thursday`，提示行对应那段同时亮——证明「提示和原句一一对应」，不是两张皮。
- **翻卡片**：把屏幕转向评委，30px 大字；翻回来是自己的释义面。

**台上不说的话**（避免过度承诺）：

- 不说「支持所有语言」——本版目标语言 4 种，做透的方向 3 个。
- 不说「谐音准确」——所有提示都标了「近似，不等同准确发音」。
- 不说「任何会议软件都支持」——只验证了抓系统默认输出这一条路径。

## 第 4 页 · 真与假：哪些是真的，哪些是模拟，哪些还没验

这一页必须有。评委问的第一个问题通常是「这是真的吗」。

| 类别 | 内容 | 状态 |
| --- | --- | --- |
| **真的** | 音频采集（WASAPI 回环）、切句、SQLite 记录与分页、读音提示引擎、双面卡、字号、无障碍焦点管理 | 有自动化测试（819 条断言）+ 真界面自检（10 步） |
| **真的** | 本机系统语音的语言核验（缺语音时明确报错，不拿别的语言顶替） | 23 条断言 |
| **模拟** | 演示模式下的字幕与回复 | 预置文本，界面有橙色横幅写明「演示模式：听不到电脑里的声音」 |
| **模拟** | 第 3 页的三条样例句 | 预置文本，不调用付费接口 |
| **没验** | 真实语音识别 + 真实翻译的端到端质量 | 服务商余额不足（HTTP 402）；本机也没有英语 TTS 语音 |
| **没验** | 日语母语者对读音的评价 | 没有可协调的母语者 |
| **没验** | 目标使用者（听障者）本人的可用性 | 未执行 |
| **没验** | 读屏软件实读、另一台干净 Windows 安装 | 未执行 |

**一句话总结这一页**：核心链路是本地、可测、可复现的；模型那一半（识别与翻译）在这台机器上发不出请求，所以不计入「已验证」。

## 第 5 页 · 团队、工具与下一步

**成员与分工**（详见《成员贡献与工具使用-v0.6.0.md》）

- 产品判断与取舍、演示脚本、目标用户访谈口径
- 前端（460×640 悬浮窗、无障碍、双面卡）
- 主进程（音频链路、SQLite 记录、IPC 安全）
- 读音引擎与回归用例（日语假名、英语片假名）

**AI 工具怎么用的**

- 用来写代码骨架、查 API、生成测试用例的结构；**每一条结论都回到代码和测试里核**。
- 被 AI 误导过的实例记在文档里：0.5.0 那 53 条发音测试全绿，却漏掉了片假名输入——因为测试只覆盖平假名。这类「测试给了虚假安全感」的情况，是这一版加片假名／未知汉字用例的直接原因。

**下一步（按优先级）**

1. 补真实链路验证：换一个有余额的账号 + 装英语语音包，跑完整「说话 → 字幕 → 回复」。
2. 找 3 位听障使用者做 30 分钟任务测试（三条样例句就是任务脚本）。
3. 日语读音请母语者过一遍，把词典外的高频词补进去。
4. 性能：回复目前是非流式，首字要等 7–9 秒，流式化是最大的一笔提速。

**已知不足，主动说明**

- 记录用的是 `delete` 回滚日志而不是 WAL（这个 WASM 构建下 WAL 不生效），写入比原生慢，但同样原子。
- 安装包没有代码签名，Windows 会提示「未知发布者」。
- Electron 33 已停止维护，升级排在性能之后。
