## 第 7 轮：0.3.2 交付后的一次战略盘点（只做分析，未改代码）

用户问「有什么要优化的 / 下一步做什么 / 加强什么方向 / 加什么创新」。做了一轮代码核实 + 方向规划，本轮**没有产生任何代码改动**。

### 核实到的关键事实（重要，后续优化都建立在这上面）

1. **整条 AI 链路完全非流式**，每一跳都是"全有或全无"：
   - `src/services/stt/openai-stt.ts#transcribe()` → `Promise<TranscriptionResult>`，无 partial
   - `src/services/translation/llm-translator.ts#translate()` → `Promise<string>`（全文仅 42 行）
   - `src/services/llm/http.ts` 里**完全没有** stream / SSE / chunk / readline 处理
   → 演示模式是本地 mock 毫秒返回，所以"跑起来流畅"是假象；真实 Key 下 STT 1.8s + 翻译 1.4s，链路追不上对话语速。
2. **端到端时延从未被测量**。全项目只有 `openai-compatible.ts#ping()` 的 `latencyMs`（那是连接测试，不是链路耗时）。
3. `logger.ts` 已有 512KB 上限自截断（`MAX_FILE_BYTES`），**不是问题**，不要再"优化"它。
4. `speakingCorrection` **只有设置项和 UI 开关，主流程没接入**（`types.ts` + `GeneralSettings.tsx` 各一处，无实现）。
5. 生词本 / 学习记录 / Conversation Summary **无任何代码**，仅为规划。
6. TTS 有两条路（`openai-tts.ts` / `web-speech.ts`），STT 只有云端一条（无本地/离线选项）。
7. 采音**单点依赖 Python sidecar**，无降级路径。

### 给出的方向判断（本轮结论）

- **第一优先级是「装秒表」而不是加功能**：加 `[Latency] stt=.. translate=.. llm=..` 埋点 + 诊断面板。没有数字后续优化都是盲调。
- **延迟优化排序**：① 翻译改 SSE 流式（首字 1.5s→0.3s）② STT partial 先翻一版 ③ **回复预取**（VAD 确认静音那 1.1~2.5s 是白等的，可提前生成；甚至用 partial 预生成"最可能的三种回应"，真需要时 0 延迟命中——代价是浪费 token，但用户买的就是即时）。
- **产品定位应从「翻译器」转向「接话教练」**：字幕软件解决"听懂"、翻译 App 解决"看懂"，**没人解决"我该说什么"**，而这正是本产品的护城河。四个创新：① 接话骨架（只给话头 "That's a good point, but..."，不给整句——真实对话里念完整句很假）② 「我没跟上」逃生舱（Alt+1/2/3 直出预设句 `Sorry, could you say that again a bit slower?`，高频刚需、零延迟、不走 AI）③ 语气自动判断（从对方那句话判抱怨/玩笑/提问并推荐语气）④ 生词自动收集 + CET4/CET6 等级标注。
- **四六级听力被评为最佳细分切入口**：需求刚性、用户明确、有真题做评价标准，且「暂停即出答案」在这里是**独占功能**（市面上没人做）。可加句级循环 A-B 复读、听力原文对照、听写模式。
- **工程命门（P0，因为这是"能不能用"）**：Electron 自带 `getDisplayMedia({ audio: true })` + `chromeMediaSource: 'desktop'`，能在 Chromium 内直接抓桌面/系统音频，**不需要任何外部进程**。建议认真评估用它做降级路径甚至取代 Python sidecar。

### 尚未验证 / 下一步

- 上面所有时延数字（1.8s/1.4s/2.1s）是**按经验估的量级，不是实测值**——必须先埋点拿到真数字再谈优化。
- `getDisplayMedia` 抓音频在 Electron 33 上的实际可行性**未验证**（需要 `session.setDisplayMediaRequestHandler`，且 Windows 上能否拿到系统 loopback 音频要实测）。这是下一步最值得做的一个技术验证。

### 更进一步的产品判断（被追问"你的想法"时给出的）

- **真正的瓶颈是"认知债"而不是技术债**：0.1.0→0.3.2 五个版本、界面改了很多轮，但**真实 Key 下的端到端流程一次都没跑通过**，也从没有真人在真实场景里用过。所有需求判断都建立在"我认为用户需要"上。
- **产品定位应再往前走一步**：不只是"接话教练"，本质是**「一个坐在旁边、会英语、特别耐心的朋友」**。人在听不懂外语时最大的情绪不是"需要翻译"，是**慌**（插不上话的尴尬）。现在产品解决的是"信息"问题，没解决"情绪"问题。「没跟上」逃生舱之所以对，是因为它给了随时撤退的安全网——知道自己能退出，人才敢开口。这个视角会反过来影响 UI：不该像仪表盘，该让用户**瞄一眼就够**；状态文案不该是"正在识别中"，该是"我在听"。
- **该做减法而不是加法**：三种场景模式（对话/看视频/四六级）很可能都是半成品，不如只留一个做透。语气选择器/发音标注等有多少真有人用，应该盘一次。到 0.3.2 这个阶段，收益最大的是"减和深"，不是"加"。
- **如果排 7 天**：D1-2 埋点拿真数字 → D3 配真 Key 跑通整条链 → D4-5 按时延构成决定做 partial / 流式 / 预取 → D6-7 加「没跟上」逃生舱（两小时成本、永不失败的底线功能）→ 然后**找一个真人看他用一小时**。
- 风险提示（给自己）：把"通用 AI 能力"（STT+翻译+LLM）当成了产品能力。这三件事拼起来不难，难的是"在正确的时刻、用正确的方式、给到正确的那句话"——**时机和方式才是产品**。

## 第 8 轮：装秒表 + 「静音下看视频仍能翻译」（本轮大量代码改动）

### 一、静音问题的实测结论（决定性，取代了上一轮的推理）

写了 `.dev/mute-loopback-test.py` 真机测（COM 精确设端点音量/静音 + soundcard 播 440Hz + 回环采集中位 RMS，含本底对照）：

```
不放任何声音（本底）        回环 RMS 0.000000
音量 100% 不静音（第一次）   RMS 0.035232  (-29.1 dBFS)
音量  50% 不静音             RMS 0.112183  (-19.0 dBFS)
音量  20% 不静音             RMS 0.270409  (-11.4 dBFS)
音量   2% 不静音             RMS 0.307753  (-10.2 dBFS)
音量 100% 静音               RMS 0.034895  (-29.1 dBFS)
音量 100% 不静音（对照）     RMS 0.034891  (-29.1 dBFS)
结论：回环取样点在端点音量/静音【之前】，三者差 1.0%（=噪声底线本身）
```
**→ 静音对采集零影响**。所以需求不需要在采集侧绕路，正解是「把状态显示出来让用户不必怀疑」+「修掉真正会丢音频的隐患」。
（副作用：本底为 0 证明量到的确实是播放的声音，不是底噪。）

### 二、真正会丢音频的隐患（已修）

旧 VAD 门槛是**固定绝对下限** `startThreshold = max(200, noiseFloor*2.4)`（200 在 int16 刻度约 -44 dBFS）。低音量素材（小声对白、纪录片环境音）**整段被当静音丢弃**，界面只会说"没听到声音"，用户以为软件坏了。
新增 `src/shared/adaptive-vad.ts`：门槛可跟随「近期峰值」往下走，但**永不高于旧的 200**（`LEGACY_CEILING=200` 现在是上限、`ABSOLUTE_FLOOR=80` 兜底、`PEAK_DECAY=0.98` 约 3.4s 半衰）。关键不变量「门槛永不比旧实现更严」（→ 字幕只会变多不会变少）由单测守着。

### 三、第一次拿到真实数字（真 Key + 真模型）

- 识别：`probeSttLatency()` 自造 3 秒音频直接打真接口 → **实时率 0.13 ~ 3.73**，模型 `FunAudioLLM/SenseVoiceSmall`。**STT 完全不是瓶颈**（比实时快 3~8 倍），上一轮"优先优化翻译/STT"的判断被推翻。
- **生成回复：平均 7.0 秒**（7 次样本，`Qwen/Qwen2.5-7B-Instruct`）→ **回复这一环才是真瓶颈**。对一个"接话"工具来说，等 7 秒话题早凉了。
- 识别/翻译无样本（沙箱采不到音）。

### 三·补：上面的 STT 结论**后来被推翻**（同一天，必须记住）

多跑几次测速，同一个模型、同一台机器、同一段 3 秒音频：

```
381ms(RTF 0.13)  11177ms(3.73)  3030ms(1.01)  5232ms(1.74)  516ms(0.17)
```

**波动 29 倍。** 所以「STT 不是瓶颈」只在好运气时成立；最慢的一次（实时率 3.73）字幕会
整体落后。**结论：识别这条腿不是"够快"，而是"极不稳定"**，这才是真正的风险点。
**教训：单次测量得出的性能结论不可信** —— 所以「测一次」的结果现在会累积成分布显示
（`LatencySnapshot.probeMs` + `PROBE_AUDIO_MS` 统一口径），体检结论也优先报最慢的那次。

回复链路的尾巴同样被暴露出来（性能页现在会显示）：**平均 8.7 秒 · 9 次 · 最慢 5% 超过
15067 毫秒**。平均值会掩盖"某次卡了十几秒"，所以卡片改成「平均 + 最慢 5%」，
`replyTailNote()` 在长尾明显时额外点出那一句。

### 五、踩到的真 bug：设置面板会被新回复抢走

### 六、自检间歇性失败的诊断方法（可复用，很值钱）

同一份代码两次运行一次全绿一次全红 → **不要去改断言，先去比对两次的日志时间线**。从 `app.log` 里捞出 SELF CHECK 前后各 30 秒的 `settings updated / reply generated / silence detected`，就能看到「回复在 14:07:29 落地，而断言在 14:07:28~36 之间跑」这种决定性证据。根因是**异步状态改动抢走了被测 DOM**，不是被测功能坏了。
配套做法：把时序敏感的规则抽成纯函数 + 单测（import `dist/` 产物），DOM 级自检只负责验证「接线没接错」。

### 三、修法：把「模型给的这一栏能不能信」抽成纯函数

`src/services/pronunciation.ts` 新增 `ipaLooksWrong` / `syllablesLookWrong` / `tidyChinese`，`enrichDraft` 里逐字段把关，**不可信就丢掉或换本地引擎重算**（提示词本来就写明 ipa 不确定可留空 → 空着比错着安全）。关键判据：

- `ipa`：白名单 `[^\x20-\x7E\u00C0-\u024F\u0250-\u02FF\u0300-\u036F]` 一票否决（干掉汉字/天城文/希腊字母）；**拼音声调符号必须单独判**（`āáǎà…` 落在拉丁扩展区，白名单拦不住，而拼音里的 ɑ/ɛ/ɦ 恰好是 IPA 字母）；抄原文；太短；一个 IPA 专属字符都没有。
- `syllables`：含中日韩/西里尔；混音标；纯标点块或以标点开头；**拼回去必须等于原句**（这条最强，能抓复制/丢词）。
- `chinesePronunciation`：混音标字母；出现 ≥2 个连续拉丁字母（"dere"/"ɑm"）。
